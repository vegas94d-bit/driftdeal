# AGENTS.md — Правила разработки driftdeal

## 1. О проекте

driftdeal — браузерная 2D top-down игра про автомобильный дрифт.

Основные технологии:
- HTML
- CSS
- JavaScript
- Canvas API
- Planck.js — физическая основа проекта

Главная цель — создать приятную simcade-физику дрифта, визуально привлекательную игру и постепенно превратить проект в качественный самостоятельный продукт.

## 2. Главные принципы работы

1. Сначала изучай существующий код, затем предлагай изменения.
2. Не переписывай работающие системы без необходимости.
3. Не создавай новые файлы, если задача этого не требует.
4. Не удаляй и не перемещай файлы без согласования.
5. Не устанавливай новые зависимости без необходимости и объяснения.
6. Предпочитай небольшие последовательные изменения масштабному рефакторингу.
7. Сохраняй совместимость между существующими системами.
8. Не утверждай, что задача выполнена, пока результат не проверен.

## 3. Работа с файлами

Для чтения и редактирования используй встроенные инструменты Cline:

- read_file
- search_files
- replace_in_file
- write_to_file

Используй PowerShell для:
- запуска проекта;
- выполнения тестов;
- проверки окружения;
- установки зависимостей;
- работы с Git;
- диагностических команд.

Не используй PowerShell и echo для передачи больших блоков HTML, CSS или JavaScript.

Не перезаписывай целый файл, если достаточно точечного изменения.

После редактирования обязательно проверь, что изменения действительно сохранены.

## 4. Порядок выполнения задач

Перед началом работы:

1. Изучи относящиеся к задаче файлы.
2. Определи зависимости и возможные последствия изменений.
3. Составь краткий план.
4. Укажи, какие файлы собираешься изменить.
5. Если изменение затрагивает архитектуру или может сломать существующие системы — сначала согласуй подход с пользователем.

Во время работы:

1. Выполняй задачу небольшими этапами.
2. Не добавляй функциональность, которую не просили.
3. Не меняй несвязанные части проекта.
4. При обнаружении проблемы сначала выясни причину.
5. Не скрывай ошибки и ограничения.

После работы:

1. Проверь изменённые файлы.
2. Проверь синтаксис JavaScript.
3. Запусти доступные тесты.
4. Если возможно, проверь результат в браузере.
5. Перечисли изменённые файлы.
6. Сообщи, что реально работает и что ещё требует проверки.

Не выдавай предположение за успешно выполненный тест.

## 5. Работа с физикой автомобиля

Целевое направление — simcade-физика с ощущением массы и инерции автомобиля.

Основные требования:

- задний привод;
- инерция автомобиля;
- продольные и боковые силы шин;
- естественная потеря сцепления;
- перенос нагрузки при разгоне и торможении;
- возможность инициировать занос рулём и газом;
- контрруление;
- возможность поддерживать занос газом;
- ручник как дополнительный инструмент;
- отсутствие ощущения карта с мгновенным рулением.

Planck.js используется как физическая основа, а не как готовый автомобильный симулятор.

Модель автомобильных шин и поведение осей необходимо реализовывать отдельно.

Не усложняй физическую модель без необходимости.

## 6. Архитектура и сохранность проекта

Основной проект — index.html.

Отдельные прототипы разрешены, если они помогают безопасно проверять новые механики.

Например:
- physics-prototype.html — экспериментальная физика автомобиля.

Экспериментальные прототипы не должны случайно ломать основной проект.

Перед переносом экспериментального решения в основную игру:
1. Проверь его работоспособность.
2. Сравни архитектуру с существующим проектом.
3. Определи необходимые изменения.
4. Согласуй перенос, если он затрагивает несколько систем.

## 7. Управление версиями

Используй Git как механизм защиты проекта.

Перед крупными изменениями:
- проверь состояние Git;
- убедись, что текущие изменения не будут потеряны;
- предложи создать контрольный коммит.

Не выполняй destructive-команды без согласования.

Не удаляй незакоммиченные изменения пользователя.

## 8. Общение с пользователем

Пользователь изучает разработку и хочет понимать, как устроен проект.

Поэтому:
- объясняй технические решения простым языком;
- не скрывай важные архитектурные решения;
- объясняй, почему выбран конкретный подход;
- не перегружай ответ ненужной теорией;
- предлагай один следующий практический шаг;
- не выдавай длинный отчёт вместо работающего результата.

Если есть несколько вариантов решения, кратко сравни их и предложи лучший.

Не принимай важные архитектурные решения самостоятельно, если они существенно меняют направление проекта.

## 9. Главная стратегия

Наша задача — не просто генерировать код.

Мы постепенно строим управляемый процесс AI-разработки, в котором агент умеет:

1. Изучать проект.
2. Планировать изменения.
3. Реализовывать функциональность.
4. Проверять результат.
5. Находить и исправлять ошибки.
6. Документировать изменения.

Приоритет — стабильный работающий продукт, а не количество написанного кода.

**Главное правило: сначала понимание, затем изменение, после этого проверка.**
